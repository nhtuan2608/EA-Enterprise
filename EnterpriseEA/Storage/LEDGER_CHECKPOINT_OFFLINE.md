# Ledger checkpoint contract (offline)

`LedgerCheckpoint.mqh` defines a versioned restore contract for the DailyResetLedger and AccountRiskLedger aggregates. It is isolated from the EA shell and does not read/write files itself. The existing `AtomicWriter.mqh` writes UTF-8 text to a temporary file and replaces the destination; `SharedStateStore.mqh` only validates a narrow empty boot state and does not restore these ledger states. This prototype leaves both existing storage modules unchanged.

The checkpoint binds config version, account epoch, opaque account identity, broker/server, currency, a monotonic checkpoint sequence, capture time/freshness, daily reset snapshot ID, account-risk source snapshot ID and source risk-content fingerprint. The payload includes the daily floors and high-water state plus account-wide risk aggregates, watermarks, mode, and block/protection flags. Restore rejects missing/incomplete fields, incompatible version or identity, stale timestamps, inconsistent risk/headroom arithmetic, and replay/sequence regression. Replaying the same sequence and fingerprint is idempotent. Rejections mark reset state UNKNOWN and ledger state POLICY_DATA_UNKNOWN, block new entries, and keep the protect-existing flag on.

The integrity marker and fingerprint are caller-supplied. The Python oracle computes SHA-256 over canonical JSON to detect changed test payloads. MQL5 receives a caller-recomputed fingerprint and compares it with the stored value; it does not implement cryptographic hashing or file parsing. A trusted serializer must define complete canonical coverage; a hash without trusted storage/verification is not authentication or cryptographic proof against a malicious rewrite. Production must canonicalize and hash all material fields and rows, write the checkpoint atomically, validate schema/integrity before restore, and persist a monotonic sequence that cannot be rolled back. Neither the fingerprint nor the embedded reconciliation markers prove broker/account truth. The checkpoint restores aggregate risk state only, not the underlying position/order/deal rows or per-position risk lineage. After restart, daily status remains UNKNOWN until the current Prague reset source is attested, and risk status remains POLICY_DATA_UNKNOWN with entries blocked until a fresh account-wide broker reconciliation arrives. Replay success never grants readiness. This does not prove actual MT5 persistence, crash recovery, or broker reconciliation.

`Tests/Fixtures/ledger-checkpoint-v1.0.0.json` and `Tests/checkpoint_oracle.py` cover clean restore, missing/torn/tampered payloads, identity mismatches, stale data, replay and sequence regression. These are offline contract checks; no MetaEditor/MT5 runtime validation is available.

For a restart during the same Prague day, the trusted reset adapter can call `EEA_ReattestRestoredDailyReset` with a freshly verified reset snapshot and its independently attested current Prague day ID. Every identity, snapshot, day, timestamp, balance, and quality field must match the historical checkpoint before the daily status returns to `OK`. If the day has advanced, the caller must use `EEA_DailyResetApply` with the next contiguous reset snapshot instead. Neither path changes the account-risk ledger's blocked status; fresh broker reconciliation is still required. A failed reattestation leaves daily status `UNKNOWN` and can be retried with corrected evidence.
