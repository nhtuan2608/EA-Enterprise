# Pending order checkpoint and restart contract (offline)

`PendingOrderCheckpoint.mqh` defines a versioned, in-memory checkpoint envelope for one `EEA_PendingState`. It is isolated from the EA shell. There is no MQL serializer/parser, file operation, broker adapter, or runtime restore yet. Its purpose is to preserve order identity, original setup deadline, bar count, fill/remainder volume, risk reservation, event cursor and cancel correlation across restart without treating the saved state as broker truth.

The v1.1 checkpoint binds intent/config, broker server, account fingerprint and order ticket. It also carries the audit tail's sequence, fingerprint, event ID and observation time. A trusted serializer must fingerprint the **entire envelope** except the fingerprint fields: schema, integrity marker, sequence, capture time, max age, audit anchor and payload. Python's synthetic oracle uses canonical JSON plus SHA-256 to exercise this contract; MQL accepts a caller-supplied recomputed fingerprint and does not verify bytes itself. This is an integrity check, not proof of authenticity or of the broker's current state.

Restore rejects missing/torn/tampered, stale, future, wrong-account or sequence-regressed checkpoints. It validates volume/risk arithmetic and status invariants. On a valid restore, it retains the stored exposure and deadline but changes status to `PENDING_RACE_UNKNOWN`, clears `audit_tail_verified` and blocks new entries. A separate pure check compares a caller-verified audit tail with the checkpoint anchor and final state fields; even a match keeps entries blocked. A corrupt checkpoint or mismatched tail also blocks new entries; if an in-memory state already exists, its recorded exposure is retained and marked unknown. When no trustworthy state exists, the account-wide gate must treat exposure as unknown until fresh broker reconciliation.

No function in this module releases the restored risk reservation or resumes the pending order. The future adapter must read active orders and order/deal history, resolve fills and cancellations that occurred while offline, compare ticket/account and event watermark, then rebuild a fresh state and account-wide risk ledger. `OnTradeTransaction` notifications alone are insufficient for restart proof because transaction arrival order is not guaranteed; use the terminal history and active order state as authoritative evidence. See [MQL5 OnTradeTransaction](https://www.mql5.com/en/docs/event_handlers/ontradetransaction) and [HistorySelect](https://www.mql5.com/en/docs/trading/historyselect).

`Tests/pending_checkpoint_tests.py` and `Tests/Fixtures/pending-order-checkpoint-v1.1.0.json` cover synthetic partial fill, cancel request, terminal order, envelope tampering, stale/wrong identity, replay, sequence regression and audit-tail binding. Python tests do not execute MQL5. MQL compile, serialized file round trip, durable audit-tail replay, crash consistency, history replay and Paper evidence remain required.
