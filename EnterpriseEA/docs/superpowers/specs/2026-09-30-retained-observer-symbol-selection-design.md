# Retained-Terminal Observer and Symbol Selection Design

**Status:** Approved in chat; implementation pending  
**Date:** 2026-09-30  
**Target:** MetaTrader 5 build 6230, VTMarkets-Demo  
**Execution authority:** Observer-only. No broker order submission, modification, cancellation, position management, or virtual/Paper execution.

## 1. Purpose

This increment replaces manual canonical-to-broker symbol entry with broker-aware discovery and multi-symbol selection, then proves the read-only observer in a retained MT5 terminal sandbox rather than Strategy Tester. One EA instance must monitor multiple selected canonical symbols, preserve the operator's selection across terminal restarts, re-resolve every broker mapping from current MT5 metadata, and perform a fresh account-wide reconciliation before publishing current observer evidence.

The increment also adds enough monotonic runtime telemetry and audit correlation to demonstrate timer refresh behavior, coalesced `OnTradeTransaction` invalidation, direct bounded-history parity, and absence of duplicate refresh completion or event backlog. It must not add Paper ledger behavior or any trading mutation API.

## 2. Existing baseline and identified gaps

The repository currently has an observer-only EA shell, pure runtime evidence contracts, read-only account/symbol/position/order/deal adapters, atomic runtime snapshot storage, timer refresh, and transaction-triggered in-memory staleness. It compiles on MetaEditor build 6230 and has produced bounded runtime evidence in Strategy Tester.

The remaining gaps are:

1. `EnterpriseEA.mq5` requires parallel `InpCanonicalSymbols` and `InpBrokerSymbols` CSV inputs. Users must know broker-decorated names and can create positional binding mistakes.
2. Existing prefix/suffix discovery is advisory and is not integrated with the runtime coordinator.
3. Native MQL5 Inputs cannot provide a dynamic broker-populated multi-select control. A chart panel is required for interactive selection.
4. Strategy Tester recreates its Files sandbox, so prior evidence does not prove checkpoint survival through a real terminal restart.
5. Runtime status does not expose a durable instance ID, monotonic refresh generation, selection revision, timer counters, or refresh-duration counters.
6. `OnTradeTransaction` marks RAM stale but does not persist an invalidation audit event or prove coalescing and later reconciliation.
7. There is no independent verifier comparing the persisted bounded snapshot with the connected demo account's current history.
8. Audit events lack refresh-generation correlation, so duplicate refresh completion and backlog cannot be rejected deterministically.

## 3. Scope

### 3.1 Included

- One canonical CSV input as the startup/default selection.
- Broker symbol discovery over all terminal symbols, including symbols outside Market Watch.
- Deterministic canonical-to-broker candidate ranking with fail-closed ambiguity handling.
- Versioned aliases for canonical names whose broker root differs, such as `DXY -> USDX`.
- Multi-symbol checkbox panel attached to the EA's chart.
- Atomic persistence of selected canonical symbols, scoped to broker server and opaque account fingerprint.
- Fresh symbol discovery and specification reads after every startup and accepted selection change.
- Retained-terminal checkpoint/restart verification.
- Monotonic refresh, timer, selection, and transaction-invalidation telemetry.
- Coalesced stale refresh after external `OnTradeTransaction` activity.
- Independent read-only comparison of runtime JSON with MT5 account, positions, orders, and bounded deals.
- Duplicate audit/backlog validation and temporary-file checks.
- Offline tests, clean MQL compilation, observer-only runtime artifacts, and traceability updates.

### 3.2 Excluded

- Order submission, modification, deletion, close, partial close, stop movement, break-even, or trailing.
- Synthetic or live external activity generated by EnterpriseEA.
- Virtual execution or Paper ledger.
- Pending-order cancellation integration.
- Dynamic risk-policy inference, setup activation, or entry permission.
- Paper/Live readiness claims.
- More than 32 selected symbols.

## 4. Safety invariants

1. `InpObserverOnly=false` refuses startup.
2. `EEA_StateCanAllowEntry` remains false in every state.
3. No project MQL source may call `OrderSend`, `OrderSendAsync`, `CTrade`, `OrderDelete`, `PositionClose`, `PositionModify`, or equivalent broker mutation APIs.
4. Persisted selection is operator intent, not evidence that the broker mapping remains valid.
5. Persisted runtime status is local evidence, not broker truth. Every startup performs fresh account, symbol, position, order, and bounded-history reads.
6. A missing, disabled, conversion-only, incomplete, or ambiguous mapping cannot become resolved automatically.
7. Selection changes are committed only after discovery, fresh reconciliation, and atomic persistence all succeed. Failure preserves the previously committed selection and leaves evidence stale or blocked.
8. `OnTradeTransaction` arrival order is never treated as authoritative broker order. Active state and bounded history are re-read.
9. External activity used for runtime proof must be initiated outside EnterpriseEA. EnterpriseEA remains read-only.
10. Raw account login, account-holder name, credentials, and secrets are not persisted in project artifacts.

## 5. Symbol discovery and resolution

### 5.1 Input contract

The shell exposes:

```mql5
input string InpCanonicalSymbols = "EURUSD,GBPUSD,XAUUSD";
input bool   InpShowSymbolPanel  = true;
```

`InpBrokerSymbols` is removed. `InpCanonicalSymbols` is a comma-separated startup/default selection. Canonical tokens are trimmed, uppercased for comparison, de-duplicated while retaining the first configured order, and limited to 32 entries. Empty, malformed, or over-capacity lists fail startup.

### 5.2 Discovery source

Discovery enumerates `SymbolsTotal(false)` and `SymbolName(index,false)` so it can inspect all broker symbols, not only currently selected Market Watch symbols. It reads description, path, trade mode, existence, custom flag, digits, point, tick size/value, contract size, volume range/step, order/expiration modes, stop/freeze levels, calculation mode, and currencies.

Discovery itself is read-only. `SymbolSelect(candidate,true)` may make a resolved symbol visible for data access but grants no execution permission.

### 5.3 Normalization and aliases

Canonical comparison uses an uppercase alphanumeric normalization for candidate matching while preserving original broker names in evidence. Versioned aliases are a small explicit table, initially including `DXY -> USDX`; aliases do not bypass ranking, tradeability, or material-spec checks.

For canonical `C`, candidate classes are:

1. exact broker name equals `C`;
2. broker name starts with `C` and has only a broker decoration suffix;
3. broker name ends with `C` and has only a broker decoration prefix;
4. normalized broker name equals a versioned alias target plus broker decoration.

Substring matches in the middle of unrelated stock or ETF names are rejected. For example, `SPX` must not silently resolve `SP500.` and `GLD` must not resolve `XAUUSD`.

### 5.4 Ranking and fail-closed behavior

Candidates receive deterministic rank in this order:

1. exact and tradeable;
2. canonical root plus suffix and tradeable;
3. prefix plus canonical root and tradeable;
4. alias-root candidate and tradeable;
5. matching but non-tradeable or conversion-only candidate.

A tradeable candidate must exist, have a supported `SYMBOL_TRADE_MODE`, and pass the material symbol-spec validation already required by `EEA_ReadRuntimeSymbolSpec`. Conversion-only descriptions and disabled trade mode are never preferred over a valid tradeable candidate.

If exactly one candidate has the best valid rank, resolution succeeds. If no candidate qualifies, status is `MISSING` or `DISABLED`. If two or more candidates share the best valid rank, status is `AMBIGUOUS`; all bounded candidates are exposed for operator review, but none is selected automatically.

On the current VTMarkets-Demo account, this rule is expected to resolve `EURUSD -> EURUSD-VIP` and `XAUUSD -> XAUUSD-VIP`, while not choosing disabled `EURUSD` or conversion-only `XAUUSD.crp`.

### 5.5 Resolution evidence

Each row records:

- canonical symbol;
- resolved broker symbol or empty value;
- resolution status and reason code;
- discovery version and alias-table version;
- broker server and opaque account fingerprint;
- description/path and trade mode;
- candidate count and bounded candidate names;
- material specification fields;
- observed timestamp and selection revision.

Any material specification change invalidates the prior evidence and forces fresh reconciliation.

## 6. Chart multi-select panel

### 6.1 UI behavior

A chart panel displays up to 32 discovered canonical rows with:

- checkbox;
- canonical symbol;
- resolved broker symbol;
- `RESOLVED`, `AMBIGUOUS`, `MISSING`, or `DISABLED` status;
- broker description;
- Refresh button;
- Apply button and concise status line.

The panel is an observer configuration surface only. It must contain no trade buttons or mutation actions.

### 6.2 Selection transaction

Checkbox edits remain a pending UI selection until Apply. Apply performs:

1. canonical list validation and de-duplication;
2. fresh broker discovery for all checked symbols;
3. rejection if any selected row is unresolved or ambiguous;
4. increment of a pending `selection_revision`;
5. invalidation of prior reconciliation evidence;
6. fresh account-wide reconciliation and material-spec validation;
7. atomic write of selection and runtime snapshots;
8. commit of the new in-memory selection only after all writes succeed;
9. audit of accepted or rejected selection change.

A failed Apply leaves the previously committed selection active, keeps new entries blocked, and displays the reason.

### 6.3 Persistence and restart

`current/symbol_selection.json` stores schema/document/config versions, broker server, opaque account fingerprint, selection revision, canonical symbols, and the last observed broker mappings. It is written atomically.

On startup, a compatible persisted selection overrides the CSV default as operator intent. An incompatible or malformed file is preserved as evidence and the CSV default is used only if valid. In all cases, stored broker mappings are discarded as authority: the runtime re-enumerates broker symbols and resolves the canonical selection again.

## 7. Retained-terminal runtime model

### 7.1 Runtime identity and monotonic fields

The runtime context and status persist:

- `runtime_instance_id`, unique per `OnInit`;
- `refresh_sequence`, incremented once per refresh attempt;
- `refresh_generation`, identifying one coalesced evidence generation;
- `selection_revision`;
- `checkpoint_written_at_utc`;
- `broker_observed_at_utc`;
- `deal_watermark` and `deal_watermark_time_msc`;
- selected-symbol fingerprint;
- `timer_tick_count`;
- `refresh_attempt_count`;
- `refresh_success_count`;
- `refresh_failure_count`;
- `last_timer_at_utc`;
- `last_refresh_duration_ms` and `max_refresh_duration_ms`;
- `consecutive_refresh_failures`;
- `transaction_callback_count`;
- `transaction_invalidation_generation`;
- `pending_refresh` and `refresh_in_progress`.

Counters are checked for nonnegative and internally consistent values. A refresh cannot run reentrantly.

### 7.2 Startup and compatible checkpoint

Startup order is:

1. open audit and establish a new runtime instance ID;
2. read account identity;
3. check retained runtime checkpoint compatibility;
4. load compatible selection intent, if present;
5. audit `RUNTIME_CHECKPOINT_OBSERVED` with `MISSING`, `INCOMPATIBLE`, or `COMPATIBLE`;
6. mark runtime `RUNTIME_RECONCILIATION_REQUIRED`;
7. perform fresh symbol discovery and broker reconciliation;
8. persist fresh snapshots and status;
9. publish `OBSERVING` only when fresh evidence validates.

A compatible checkpoint never directly publishes `OBSERVING`. Acceptance requires a new runtime instance ID and a broker observation timestamp later than the prior checkpoint timestamp.

### 7.3 Timer scheduling

`OnTimer` increments `timer_tick_count`, records `last_timer_at_utc`, and schedules one refresh when evidence is stale or the refresh interval elapsed. If a refresh is already in progress, it sets `pending_refresh` but does not recurse or enqueue unbounded work. When the active refresh completes, at most one coalesced pending generation may run on a later event turn.

A normal timer tick with no due/stale evidence produces no refresh audit event. Snapshot writes remain outside `OnTick`.

### 7.4 Transaction invalidation

`OnTradeTransaction` performs no broker read or write. It:

1. increments `transaction_callback_count`;
2. marks current reconciliation stale;
3. increments `transaction_invalidation_generation` only when transitioning from current to stale;
4. sets `pending_refresh=true`;
5. emits one `BROKER_TRANSACTION_OBSERVED` audit event for that invalidation generation.

Additional callbacks received while the same invalidation generation remains pending are coalesced. The next timer-driven fresh reconciliation emits one `TRANSACTION_INVALIDATION_RECONCILED` completion tied to that generation. Callback arrival order is not used as broker history order.

## 8. Audit correlation and backlog rules

Runtime audit details include:

- runtime instance ID;
- refresh sequence and generation;
- refresh trigger (`STARTUP`, `TIMER`, `TRANSACTION`, `SELECTION_CHANGE`, `MANUAL_REFRESH`);
- selection revision;
- transaction invalidation generation;
- broker observation timestamp;
- status/reason and counter snapshot.

For each runtime instance:

1. refresh sequence and generation never decrease;
2. each refresh generation has at most one completion;
3. every completion has exactly one attempt;
4. a transaction invalidation has at most one corresponding reconciliation completion;
5. timer and stale conditions observed together create one refresh attempt;
6. exact duplicate JSONL records are invalid;
7. every audit line must parse as one complete JSON object;
8. no `.tmp` or `.recover.tmp` file may remain after the runtime is stable.

## 9. Independent retained-terminal verification

### 9.1 Attachment

Deploy the compiled observer to the connected terminal data path and attach one EA instance to a dedicated chart/profile without replacing unrelated charts. Use observer mode, a 30-second refresh, seven-day history, and a dedicated data root. Capture pre-attachment account balance/equity, positions, and pending-order ticket sets.

### 9.2 Checkpoint survival and fresh reconciliation

1. Wait for at least two successful timer refreshes.
2. Preserve the status/checkpoint hash, runtime instance ID, refresh generation, checkpoint timestamp, and broker observation timestamp.
3. Close and restart the same terminal normally.
4. Confirm the retained file exists before the restarted EA writes fresh evidence.
5. Confirm `RUNTIME_CHECKPOINT_OBSERVED/COMPATIBLE` appears before a fresh refresh completion.
6. Confirm the new runtime instance ID differs and the new broker observation time is later.
7. Confirm the runtime reaches `OBSERVING` only after the fresh read and persistence succeed.

### 9.3 Timer soak

Run the retained observer for at least 60 continuous minutes with a 30-second interval. Expected behavior:

- at least 100 successful periodic refreshes unless the terminal is disconnected;
- monotonic counter/generation progression;
- zero overlapping refresh attempts;
- no unexplained refresh-generation gaps;
- no growing pending-refresh backlog;
- no leftover temporary files;
- failures, if any, are explicitly counted and audited rather than hidden.

### 9.4 External transaction activity

EnterpriseEA must not create the activity. A user action, another EA, or an already existing external demo workflow may create one demo account transaction. The proof requires `BROKER_TRANSACTION_OBSERVED`, one coalesced fresh reconciliation, and `TRANSACTION_INVALIDATION_RECONCILED`, with the account snapshot reflecting authoritative MT5 state.

If no external transaction is available during the verification window, the implementation may be complete but this acceptance item remains `RUNTIME_EVIDENCE_PENDING`; it must not be simulated or claimed as observed.

### 9.5 Direct bounded snapshot parity

A read-only verifier compares the persisted reconciliation document with an independent connected-terminal read over the same declared lookback end time. It compares:

- opaque server/currency/margin identity;
- position ticket set and count;
- active-order ticket set and count;
- deal ticket set/count and `(time_msc,ticket)` ordering;
- deal watermark and watermark time;
- history window bounds;
- selected canonical-to-broker mappings and material symbol fields.

Time-sensitive price/profit values may be reported but are not equality keys. The verifier stores no raw login or account-holder name.

### 9.6 No-side-effect comparison

After verification, capture balance/equity, position tickets, and pending-order tickets again. Any change is attributed only after comparing deal/order history and external-activity evidence. EnterpriseEA must have no mutation API and no audit event claiming a trade action.

## 10. Testing strategy

### 10.1 Offline TDD

Tests are written and observed failing before production changes. They cover:

- canonical CSV normalization, duplicate removal, capacity, and malformed inputs;
- exact, suffix, prefix, alias, disabled, conversion-only, missing, and ambiguous discovery cases;
- current VTMarkets-style examples (`EURUSD-VIP`, `XAUUSD-VIP`, `XAUUSD.crp`, `SP500.`);
- selection atomic commit/rollback semantics;
- compatible/incompatible persisted selection behavior;
- startup checkpoint ordering and mandatory fresh reconciliation;
- monotonic timer/refresh counters;
- transaction invalidation coalescing;
- one attempt/one completion per generation;
- duplicate audit and backlog rejection;
- static absence of mutation APIs;
- panel event routing restricted to selection/refresh actions.

### 10.2 Compiler verification

Compile `EnterpriseEA.mq5` with MetaEditor build 6230. Acceptance is zero errors and zero warnings after reviewing the build log.

### 10.3 Runtime verification artifacts

Artifacts include:

- compiler log;
- retained-terminal runbook and timestamped observation log;
- before/restart/after redacted status and reconciliation snapshots;
- symbol discovery/selection evidence;
- audit verifier result;
- bounded-history parity result;
- pre/post account and ticket-set comparison;
- explicit status for external transaction invalidation evidence.

## 11. Acceptance criteria

1. `InpBrokerSymbols` no longer exists; canonical CSV is the only symbol-name input.
2. The EA automatically resolves a unique best broker symbol and fails closed on missing or ambiguous mappings.
3. One attached EA instance observes all selected symbols up to the 32-symbol bound.
4. The checkbox panel can stage and atomically apply a multi-symbol selection.
5. A compatible persisted selection survives a real terminal restart but all broker mappings are rediscovered.
6. A retained runtime checkpoint survives restart and is observed as compatible.
7. Compatible checkpoint handling still performs fresh broker reconciliation before `OBSERVING`.
8. A 60-minute timer soak satisfies monotonicity, no-overlap, no-backlog, and no-temp-file checks.
9. External `OnTradeTransaction` activity is either proved through coalesced invalidation/reconciliation or explicitly marked pending if no outside activity is available.
10. Persisted bounded snapshot matches an independent demo account/history read for identity and ticket/watermark keys.
11. Audit verification finds no duplicate completion, exact duplicate record, unexplained generation gap, or unresolved pending generation.
12. The full offline suite passes and MetaEditor reports zero errors and zero warnings.
13. Static scanning confirms no execution/cancellation/position-management API.
14. Account balance, positions, and orders show no side effect caused by EnterpriseEA.
15. Documentation continues to mark virtual/Paper execution and pending-order submission/cancellation as not implemented.

## 12. Evidence classification

After source/test/compile completion:

- symbol discovery and selection: `OFFLINE_VERIFIED`, `MQL_COMPILED`;
- retained checkpoint and timer behavior: `RUNTIME_OBSERVED` only after retained-terminal artifacts pass;
- account/position/order/deal evidence: `BROKER_RECONCILED_BOUNDED` only for the declared lookback and parity keys;
- external transaction invalidation: `RUNTIME_OBSERVED` only when genuine external activity is captured, otherwise `RUNTIME_EVIDENCE_PENDING`;
- virtual/Paper ledger: `PAPER_PENDING` and not implemented;
- broker order submission/modification/cancellation: `NOT_IMPLEMENTED`.

No result from this increment grants Paper or Live permission.
