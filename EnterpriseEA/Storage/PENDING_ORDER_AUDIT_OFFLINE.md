# Pending order transition audit contract (offline)

`PendingOrderAudit.mqh` is a pure append contract for one pending order. The first record must be `SEED_ACCEPTED`; later records cover a closed bar, guard snapshot, timer, broker fill, cancel request, broker terminal confirmation, restore, unknown state or reconciliation evidence. Each record binds the intent, candidate, setup/config/instrument versions, broker server, account fingerprint, order ticket, state before/after, reason, original expiry, bar count, broker event sequence, filled/cancelled/remaining volume and risk reservation. A failed validation marks the supplied resulting state `PENDING_RACE_UNKNOWN`, blocks entries and blocks further use of that audit cursor.

The cursor requires a contiguous audit sequence and previous-record fingerprint. The caller's serializer must recompute a fingerprint over the whole record except its fingerprint fields and persist accepted records durably before relying on a transition. An exact duplicate of the most recent record is idempotent; a gap, changed fingerprint, repeated event ID, wrong ticket, inconsistent volume/risk delta or illegal transition fails closed. The Python oracle signs synthetic canonical JSON with SHA-256. The MQL module only compares caller-supplied fingerprints; it neither hashes bytes nor writes JSONL. An unkeyed hash is an integrity aid, not proof that the broker supplied an event.

`RECONCILE_EVIDENCE` requires a broker snapshot ID plus order-history and deal-set fingerprints. It records that evidence was presented while keeping the order `PENDING_RACE_UNKNOWN` and entries blocked. It **does not** decide that history is complete, release risk, reconstruct missed fills or re-enable the order. Those decisions need an MT5 adapter that reads active orders and order/deal history, resolves the account/ticket and all fills, then updates the account-wide ledger. [MQL5 documents that `OnTradeTransaction` arrival order is not guaranteed](https://www.mql5.com/en/docs/event_handlers/ontradetransaction), so the future adapter must not use callback arrival order as the audit sequence.

`Tests/Fixtures/pending-order-audit-v1.0.0.json`, `pending_audit_oracle.py` and `pending_audit_tests.py` cover synthetic chains, duplicate/gap/conflict, forged risk release, ticket mismatch, restart and reconciliation evidence. The EA shell does not include this module. There is no MQL compilation, persistent audit append, file recovery, broker history read or Paper evidence yet. The v1.1 pending checkpoint now carries an audit-tail anchor and checks it against a caller-verified final record after restore. Runtime use still requires durable audit-cursor persistence or reconstruction of the **entire verified chain**; matching only its final record is insufficient.
